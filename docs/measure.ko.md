# 내 지식 베이스에서 Cairn 측정하기

한국어 · [English](measure.md)

논문은 지식 베이스 하나에서만 Cairn을 쟀습니다. 내 지식 베이스에서도 비용이 줄지는 노트, 질문 구성, 에이전트 하네스, 검색 방식에 달려 있습니다. 이 문서는 직접 돌려 볼 수 있는 비교 방법을 설명합니다. 통계는 [`scripts/measure.mjs`](../scripts/measure.mjs)가 실행 기록을 담은 평범한 JSONL 파일에서 계산합니다.

## 비교 대상

- **기준(baseline)**: 지금 에이전트가 쓰는 구성. 예를 들어 파일 도구로 읽는 원본 노트, 검색 명령만, 또는 둘 다.
- **Cairn**: 같은 구성에 생성된 볼트와 길 안내 블록을 더한 것.

두 구성의 나머지 조건은 모두 같게 둡니다. 모델, 하네스와 그 버전, 도구와 권한, 턴 제한, 시스템 프롬프트(길 안내 블록만 다름), 지식 베이스 버전이 모두 같아야 합니다. 감사 규칙(예: "볼트를 셸 명령으로 읽지 않기")을 둔다면 Cairn에만 걸지 말고 두 구성 모두에 적용합니다.

## 질문

1. **결과를 보기 전에 질문 세트를 고정하고**, 질문 파일의 해시를 기록합니다.
2. **네 가지 질문 종류를 모두 넣습니다**: 주제 조회, 속성 필터, 관계 조회, 여러 노드 조합. 실제 질문 비율을 알면 거기에 맞추고, 모르면 종류별 결과를 따로 보고합니다. 전체 수치는 이 비율에 따라 달라지기 때문입니다.
3. **가능하면 설계에 쓰지 않은 질문을 따로 둡니다.** 어떤 질문을 보면서 카드나 규칙을 다듬은 뒤 같은 질문으로 재면 결과가 Cairn에 유리하게 나옵니다(논문의 질문도 설계와 겹쳤고, 논문은 이를 한계로 밝혔습니다).
4. **정답은 가능한 한 기계적으로 만듭니다.** 속성 질문과 관계 질문은 관련 노드 id를 손으로 고르지 말고 front matter에서 계산합니다.

## 실행

- **두 구성을 같은 기간에, 순서를 무작위로 섞어 실행합니다.** 논문에서는 프롬프트가 똑같은 기준 구성이 몇 시간 간격으로 잰 두 측정 사이에 13.6% 움직였습니다. 같은 시기에 돌리지 않은 기준은 실제 효과를 가리기도 하고, 없는 효과를 만들어 내기도 합니다.
- **질문마다 여러 번(최소 세 번) 실행합니다.** 한 번씩만 돌리면 잡음이 큽니다. 논문에서 반복 실행 사이의 질문별 로그 표준편차는 약 0.22에서 0.24였고, 같은 비교를 세 번 잰 결과는 감소 폭이 17.7%에서 37.0%까지 달랐습니다.
- **실행별 기록**: 질문 id, 질문 종류, 구성, 실행 번호, 토큰(입력, 출력, 캐시 쓰기, 캐시 읽기, 또는 그 합), 정가 환산 비용, API 요청 수(병렬 도구 호출은 한 번으로 셉니다), 도구 호출 수, 답에 담긴 노드 id의 순위 목록, 시작과 끝의 볼트 지문(`.cairn-fingerprint.json`).
- **검색 품질도 채점합니다.** 답을 보고 Recall@5, 첫 번째 관련 노드의 역순위(reciprocal rank) 같은 값을 계산합니다. 관련 노드를 놓치면서 비용만 줄었다면 나아진 것이 아닙니다.

## 통계

대표 수치는 **같은 질문들에서 구한 평균 비용의 비에서 1을 뺀 값**입니다.

```
change = mean_q(cost_cairn(q)) / mean_q(cost_baseline(q)) − 1
```

여기서 각 `cost(q)`는 그 질문의 여러 실행을 평균한 값입니다. 평균의 비는 비싼 질문이 좌우하므로, 질문 종류별 변화도 함께 보고합니다.

불확실성은 **질문 단위로 짝지은 부트스트랩**으로 구합니다. 질문을 복원 추출하고(두 구성의 값은 함께 뽑습니다) 비를 다시 계산하는 일을 10,000번 반복한 뒤, 2.5번째와 97.5번째 백분위수를 구간으로 잡습니다. 이 구간에는 질문 사이의 변동과 실행 잡음만 들어 있고, 시간에 따른 변화나 튜닝 과정에서 생긴 선택의 영향은 들어 있지 않습니다. 그러니 불확실성의 하한으로 보세요.

## JSONL 형식과 스크립트

한 줄에 JSON 객체 하나를 씁니다. `question`과 `arm`은 필수이고, 지표는 숫자 필드라면 무엇이든 됩니다.

```json
{"question": "Q-01", "type": "relation", "arm": "baseline", "run": 1, "tokens": 51234, "cost_usd": 0.0631, "requests": 3}
{"question": "Q-01", "type": "relation", "arm": "cairn", "run": 1, "tokens": 18011, "cost_usd": 0.0262, "requests": 2}
```

```sh
node scripts/measure.mjs runs.jsonl --baseline baseline --treatment cairn \
  --metrics tokens,cost_usd,requests --by type --resamples 10000 --seed 20261013
```

출력에는 지표와 그룹마다 짝지은 질문 수, 두 평균, 변화, 그 95% 신뢰구간이 나옵니다. 두 구성 모두에서 실행하지 않은 질문은 계산에서 빼고 목록으로 알려 줍니다. 기계가 읽을 출력이 필요하면 `--json`을 붙입니다.

[`sample-runs.synthetic.jsonl`](sample-runs.synthetic.jsonl)은 형식 예시입니다. **숫자는 설명을 위해 지어낸 것**이며 결과가 아닙니다.

## 결과 해석

- 구간이 0을 포함하면 감소는 확인되지 않은 것입니다.
- 질문마다 한 번씩만 실행했다면 방향만 보고하고, 크기는 보고하지 않습니다.
- 비용과 토큰은 따로 확인합니다. 프롬프트 캐싱을 쓰면 캐시 쓰기가 정가 환산 비용의 큰 몫을 차지할 수 있어서, 두 값이 다르게 움직이기도 합니다.
- 결정하기 전에 종류별 결과를 실제 질문 비율에 맞춰 봅니다. 논문 조건에서는 주제 질문에서 줄어든 비용이 작았고, 이 질문들에서는 검색만 쓰는 구성이 더 쌌습니다.
